Pump Select Design

Decisions behind the modern version on the compare page. Each item explains what we changed from legacy IntelliQuip and why.

Removals

Legacy controls we intentionally don't carry forward. Each one is still listed on the compare page so the inventory stays 1:1.

Use service factor

LegacyA checkbox next to the Service factor dropdown decides whether the factor applies.ModernOne Service factor dropdown: None, 1.15, 1.20, 1.25.WhyOff just means 1.00. One control states the value directly, with no separate switch to find or keep in order.

Transfer to COS

LegacyA button under the Head Loss Module copies its results back to Conditions of Service.ModernRemoved. Head loss results stay linked to Head, NPSH available and Suction pressure (see Controlled inputs).WhyThe button only exists because the calculator is a separate form. Manual syncing means values silently go stale when someone forgets to click it.

50 Hz and 60 Hz speed fields

LegacySeparate synchronous speed fields for each supply frequency.ModernOne field per purpose whose options follow Frequency.WhyOnly one set is ever relevant, so the second set is noise.

Per-field Calculate radios

LegacyA Calculate radio next to each of five slurry values.ModernTwo dropdowns: Calculate density and Calculate concentration.WhyThe five radios are really two exclusive groups. A dropdown names each choice once instead of scattering it across rows.

Deprecated controls

LegacyCancel, Next, Next button blink, Language selector display, Selector callback max.ModernNot ported.WhyUsed by 0 of 156 customers.

Controlled inputs

Many fields are calculated from other fields, often ones far away on the page or in a different tool. Liquid properties fill density and viscosity. Head loss fills Head. Duty point fills the first row of Multiple conditions. People need to see that a field is part of a relationship, find the other end, and know when a value no longer matches its calculation.

Color: teal, not purple

Purple has become the industry shorthand for AI, and this product family has AI agents, so purple would make a calculated value read as AI-generated. Blue already means links, focus and primary actions. Amber is reserved for the overridden state, red for errors, green for success. Teal is unclaimed and reads as "systematic". It's one token (--relation) so it's easy to change.

Our pattern

All of these are live on the compare page. Try changing Flow in Duty point, Max temperature in Liquid properties, or typing over Viscosity in Fluid.

1. Field marker

Affordance: calculated fields get a teal tint and an ƒx button; fields that feed others get a → button. Behavior: the button opens the relationship popover. A field can show both roles.

2. Popover with jump links

Calculated from:

Calculates to:

Affordance: "Calculated from:" and "Calculates to:" lists, each entry named by card and field. Behavior: clicking an entry jumps to that field. Hidden fields say so instead of jumping.

3. Jump and return

Affordance: a back pill in the bottom-left corner. Behavior: a jump scrolls the target to the middle of the screen, focuses it and flashes it. The pill returns you to where you started, then disappears.

4. Dependent highlighting

Affordance: while you're in a field, every related field gets a teal ring. Behavior: if any are off screen, a chip in the bottom-right counts them and jumps to the first.

5. Overridden state

Calculated from:

Affordance: typing over a calculated value turns the field amber with a ≠ marker. Behavior: the field stops following its source. "Use calculated" in the popover restores the link and the calculated value.

6. Change notice

Affordance: calculated fields flash teal when their value changes. Behavior: if any changed fields are off screen, a toast says how many and jumps to them. Changes chain, so a change can update fields that depend on other calculated fields.

7. Relationship overlay

Affordance: a "Show relationships" toggle in the top-right corner. Behavior: draws a teal curve between every source and calculated field on the page. Useful for auditing and onboarding, too noisy to leave on.

Data validation requests to product / engineering

The controlled-input pattern only works if the data model says which fields are calculated from which. Today the compare page runs on 38 relationships we inferred from legacy screens. Before we commit to the pattern, we need the real equivalents of calculatedFrom and calculatesTo for every relevant field in the initial delivery scope (Release A: app shell, duty point, fluid, speed configuration, operating constraints, driver sizing, selection filters).

For each calculated field, we need

  • The fields it's calculated from, including fields on other screens or tools.
  • The fields it calculates to, so we can show "Calculates to:" without inverting a formula.
  • Whether it's a direct copy, a formula, or a lookup (for example, the liquid property database).
  • Whether users can override it, and whether an override survives later changes to its sources.
  • When the link applies. Some links only exist while a tool is in use, like head loss filling Head.
  • When it recalculates: on every change, on submit, or on the next search.

Relationships we assumed and need confirmed

  • Liquid type and temperatures → density, viscosity, vapor pressure.
  • Frequency → which synchronous speeds are offered.
  • NPSH calculator inputs → NPSH available.
  • Head loss results → Head, NPSH available, suction pressure (the old Transfer to COS mapping).
  • Duty point → Multiple conditions row 1 and interstage final discharge.
  • Margin, service factor and density strategy → driver size.

Without this list, the UI can show the pattern but can't promise every calculated field is marked, which defeats the point of marking any of them.
